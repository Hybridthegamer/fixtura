# FIXTURA — Implementation Decisions

Choices made where the build brief was silent, as required by §0 rule 6.

## 2026-08-08

1. **Next.js 16 instead of 15.** Latest stable at scaffolding time. Backward-compatible with the brief's App Router, RSC, and Server Actions requirements.

2. **Tailwind CSS v4 with `@theme`.** v4 uses CSS-first configuration via `@theme` blocks, replacing `tailwind.config.ts`. Design tokens from §2.3 are declared directly in `globals.css`.

3. **Lucide React for icons.** Lightweight, tree-shakeable, matches the broadcast aesthetic.

4. **Zustand for client state.** Minimal state management for the results console offline queue and optimistic updates. No Redux — overkill for the data shapes here.

5. **react-hot-toast for notifications.** In-app toast notifications. Lightweight, accessible.

6. **class-variance-authority + clsx + tailwind-merge** for component variants following shadcn/ui patterns.

7. **No shadcn/ui CLI init.** Building primitives directly from the brief's spec. The styling is too specific to use default shadcn — everything must look like Fixtura, not like shadcn.

8. **Prisma v7 with `@prisma/adapter-neon`.** Latest stable at time of build. The adapter is included but the neon driver import pattern in v7 differs slightly from the brief; using `@prisma/adapter-neon` with `Pool` from `@neondatabase/serverless`.

9. **Auth.js v5 (next-auth@beta).** The beta tag is required for App Router compatibility. The brief says "Auth.js v5 (NextAuth)" — the package is `next-auth@beta`.

10. **TypeScript `target: "ES2017"`** as the scaffold generated. The brief doesn't specify, and this is the Next.js default. Adequate for all target browsers.

11. **No `srcDir` flag misinterpretation.** We're using `src/` directory (what Next.js calls `srcDir`), which the scaffold created correctly.

12. **Database: SQLite for local dev, Neon for production.** Since we don't have a Neon connection in this environment, we'll use SQLite for local development and testing. Prisma schema supports both with a simple provider swap. The engine tests (§14) need no database at all.

## 2026-08-15 — Verification pass against the brief

Audited the existing implementation against every section of the brief. §6 (the format engine) had the most serious gap: `onResult` — the bracket-progression method the brief's own `FormatAdapter` interface requires — didn't exist anywhere in the codebase, and the §14 test file had been written with loosened assertions (`toBeLessThanOrEqual`, `toBeGreaterThan`) that happened to pass around that hole rather than catching it. Concretely, `SINGLE_ELIMINATION` and `DOUBLE_ELIMINATION` generated only round 1 correctly; every later round was a permanently-empty fixture shell, and round-1 byes vanished from the bracket instead of advancing. `GROUPS_KNOCKOUT`'s knockout stage had the same problem, and `SWISS` generated all rounds up front from the seed alone — structurally impossible, since Swiss pairings depend on standings after each round.

Given rule 2 ("If you compromise anywhere, do not compromise there"), this was fixed rather than left as a gap:

13. **`lib/engine/bracket.ts`** is a new shared module: `standardSeedOrder` (the recursive 1-vs-16/8-vs-9 seeding table), `buildEliminationBracket` (shells rounds 2+, resolves round-1 byes immediately, shared by `SINGLE_ELIMINATION` and the `GROUPS_KNOCKOUT` knockout stage), and `eliminationOnResult` (winner advancement + third-place-playoff feed, shared by both).

14. **`SINGLE_ELIMINATION`, `GROUPS_KNOCKOUT`, `SWISS`, `DOUBLE_ELIMINATION` now build later rounds lazily via `onResult`**, not entirely at `plan()` time, because who plays whom in round *N* genuinely depends on round *N-1*'s results (or, for groups→knockout, on final group standings). `plan()` still returns a deterministic seed-derived structure — round 1 for elimination formats, the full group stage for groups→knockout — and `EngineState` gained an optional `formatConfig` field so `SWISS.onResult` can look up the configured round count without threading it through a wider interface change. Fixture and round *counts* are always known up front (`n-1` for single elim, `2n-2` for double elim, etc.); only the round *contents* are filled in incrementally.

15. **`DOUBLE_ELIMINATION`'s losers-bracket drop map** (§6.2: "the format most implementations get subtly wrong") is built from k (winners-bracket rounds) via an explicit round-kind sequence (`seed` → `drop`/`pure` alternation), with round *widths* computed dynamically rather than from a closed-form formula — necessary because a non-power-of-two field (e.g. n=12) gives WB round 1 byes, which means fewer WB1 losers than a clean bracket would produce, which desynchronizes the LB round-1 survivor count from WB round 2's loser count. When a drop round's two incoming groups are unequal, the shorter list is matched 1:1 against a same-size slice of the longer list (Kuhn's algorithm, avoiding any repeat pairing), and the leftover overflow is paired among itself, carrying a lone leftover straight to the next round as an unopposed bye fixture — mirroring how WB round-1 byes are represented. Rematch avoidance itself uses real matching algorithms (Kuhn's augmenting-path algorithm across two lists, backtracking within one list) rather than a greedy first-fit, because greedy pairing can leave a *forced* rematch even when a rematch-free assignment exists elsewhere in the search space (caught by the randomized simulation test, then fixed). Two rematch scenarios are mathematically unavoidable regardless of algorithm and are documented rather than "fixed": at n=4, LB round 2 has exactly one survivor and one WB-final loser with no alternative opponent; more generally, a "pure" LB round can narrow to exactly the two entrants who happen to have met earlier. The Grand Final (and its optional reset) is a deliberate third exception — it can legitimately replay an earlier pairing, including a WB-round-1 meeting, whenever the same two entrants are simply the field's best two.

16. **Tiebreaker resolution in `CROSS_SQUAD_INDIVIDUAL_RR` was silently faking winners on unbreakable N-way ties.** The rank-assignment step re-checked whether adjacent rows were "separated" by re-running each tiebreaker rule on just that *pair*, rather than using the outcome already computed for the full tied group. That's wrong for 3+-way ties: a perfect three-way cyclic tie (A beat B, B beat C, C beat A — all level on every metric including the head-to-head mini-table) got resolved into a fake 1-2-3 order, because checking any two of the three pairwise showed a real, if locally misleading, separation. Fixed by having the tiebreaker cascade tag every row with an explicit tie-group id as it resolves (`resolveTieGroup` in `crossSquadRR.ts`), and using that id — not a pairwise re-check — to decide shared ranks. Caught by a new test constructing exactly this cycle.

17. **Points are now configurable end-to-end (§6.7).** `FormatAdapter.standings()` gained an optional `pointsConfig` (`{win, draw, loss}`, default 3/1/0) parameter, threaded through `CROSS_SQUAD_INDIVIDUAL_RR` (including its head-to-head mini-table, which previously hardcoded 3/1/0 independently of the primary scoring — an organizer changing point values would have gotten an inconsistent tiebreak), `ROUND_ROBIN`, `SWISS`, and `GROUPS_KNOCKOUT`. Elimination formats (`SINGLE_ELIMINATION`, `DOUBLE_ELIMINATION`) score wins/losses, not points, so the parameter is accepted for interface consistency but unused there.

18. **`lib/services/results.ts` now delegates to the engine instead of re-deriving standings math in the DB layer.** The previous `recomputeStandings` was a hand-rolled reimplementation — dual-attribution round-robin math with no tiebreaker cascade beyond points/GD/GF, no head-to-head, no bracket awareness — that silently diverged from the tested `lib/engine/**` functions it was supposed to be "the same math" as (§6.7: "Both must be derived from the same immutable match rows"). It's replaced with two calls to the tournament's `getFormatAdapter(...).standings(...)` — one with `tiebreakersSquad`, one with `tiebreakersIndividual`, since a single call applies one rule list to both scopes — and renamed/exported as `recomputeAllStandings`, matching §6.7's explicit call for that escape hatch. Verified against the seeded NACOS tournament: dual attribution, configurable points, and shared-rank ties all materialize correctly through the real transaction path.

19. **Fixed a live authorization bypass in `assertCan` (§11).** The tenancy check was `if (resourceOrgId && actor.orgId && resourceOrgId !== actor.orgId)` — if `actor.orgId` was ever falsy (unset), the entire check was skipped and access silently granted, regardless of role or which org the resource belonged to. Exactly the failure mode §11 warns about ("a missing guard is the most likely serious bug in this codebase"). Fixed to require `actor.orgId === resourceOrgId` for any non-exempt org-scoped action, with a regression test.

20. **`enterResult` (the results-console mutation) had no auth guard, no tenancy check, no input validation, and no audit log at all** — any unauthenticated request could call it directly and rewrite a match result. Added a Zod input schema, a session check, a tenancy-scoped `assertCan("results:enter", ...)` guard (role re-derived from `OrgMember`, never trusted from the client), and an `AuditLog` write with before/after — matching §11's "every mutation... auth guard → tenancy guard" and §4.4's "every result write is audit-logged." Added the same guard to the `/manage/[tournamentSlug]/results` page itself (plus a session check on the whole `/manage` layout, which had none), as defense in depth beyond the action-level guard.

21. **The seed script created zero fixtures.** §15 requires seed data that is "both the demo and the regression fixture," and Phase 1 explicitly calls for a "seed script that creates the NACOS tournament end to end" — but it stopped at registrations, never calling the format engine at all. Fixed to call `crossSquadIndividualRR.plan()` with the tournament's actual seed (42) and persist the resulting gameweeks, squad matchups, and matches, advancing the tournament to `LIVE`. Verified: 150 matches across 3 gameweeks, 2 matchups/gameweek, 15 matches per player — exactly the brief's NACOS numbers.

22. **§14's own test file was rewritten to assert the brief's actual numbers**, not loosened bounds: single elimination n=16 now asserts exactly 15 matches (not `≤ 16`); n=12 asserts the 4 named seeds get byes and never meet before the final, checked via a real bracket simulation, not just a smoke test; double elimination asserts exactly 14/15 matches (not `≥ 14`); double elimination gained a randomized simulation (n=4,8,12,16, 15 trials each) checking "no entrant eliminated before losing twice" and "losers-bracket round 1 is never a rematch" — the two invariants that hold unconditionally — plus a separate deterministic test proving the drop-map's matching algorithm finds a rematch-free pairing whenever one exists; groups→knockout asserts the exact 24+7=31 match count and that no knockout pairing is between two players from the same group; Swiss is played out round-by-round through `onResult` and asserts exactly 32 matches with zero rematches. A new `src/lib/auth/__tests__/roles.test.ts` locks in the tenancy fix and the brief's explicit authorization acceptance criteria (ORG_ADMIN cross-org denial, CAPTAIN can't enter results, PLAYER can't approve registrations, ORG_ADMIN can't change payout bank details).

### What this pass did not attempt

The brief is far larger than what had been built before this pass — Phase 1 (mostly) and Phase 2 (engine) existed; Phase 3 onward was thin. This pass fixed concrete, verifiable bugs in what existed rather than building the remaining phases from scratch, which would be a substantially larger undertaking than an audit-and-fix pass. Not built, and not covered by anything above: Paystack/Monnify payments (§5) and the entire money path (webhooks, slot holds, refunds, platform fee); most `/manage/*` and `/dashboard` screens (registrations, squads, fixtures generator, disputes, announcements, prizes, graphics, settings); a fixture-generation service wiring `plan()` output to the DB for organizer-created (non-seed) tournaments; awards computation (§6.7's `SQUAD_CHAMPION`/`BEST_INDIVIDUAL`/`GOLDEN_BOOT`/`IRON_GLOVE`); notifications, share graphics, OG images; rate limiting (§11) and security headers (CSP/HSTS/etc.); the disputes flow; organizer verification and public profiles; CSV/ICS exports; and the Playwright end-to-end suite. Anyone picking this up next should treat §12's phase order as the plan: it's still accurate.
